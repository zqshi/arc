# Arc v1 — AI驱动的待办工作台

## 1. 背景与问题

**目标用户**：具备AI编程能力的产品经理/独立开发者

**核心痛点**：
- 待办以备忘录形式记录，缺乏结构，无法被AI系统消费
- 需求分析的产出与开发执行之间存在上下文断裂——分析完还得手动把结论喂给Coding Agent
- 开发过程中的决策和经验散落在聊天记录、笔记中，下次遇到类似需求无法复用

**产品定位**：以待办为核心的AI工作台，打通"记录 → 分析 → 执行 → 沉淀"四个环节的上下文链路。

## 2. 第一版范围（MVP）

### 2.1 结构化待办管理

**待办不是一行文字，而是一张需求卡片。**

待办卡片包含：
| 字段 | 说明 | 来源 |
|------|------|------|
| 标题 | 一句话描述 | 用户输入 |
| 背景 | 为什么要做这件事 | 用户输入 / AI辅助补充 |
| 目标 | 做完后达成什么效果 | 用户输入 / AI辅助补充 |
| 边界条件 | 不做什么、约束是什么 | AI辅助澄清 |
| 验收标准 | 怎么算做完了 | AI辅助生成 |
| 技术方案 | 实现路径 | AI生成 / 用户确认 |
| 执行日志 | 开发过程记录 | Coding Agent回写 |
| 状态 | 待分析 / 分析中 / 待开发 / 开发中 / 待验收 / 已完成 | 系统流转 |
| 关联待办 | 前置/后续依赖 | 用户设置 |

### 2.2 AI辅助需求澄清

用户输入一段粗略的需求描述后，AI通过多轮对话帮助：
- 识别模糊点并提出澄清问题
- 拆解需求为可执行的子任务
- 生成边界条件和验收标准
- 产出结构化的待办卡片

**关键交互**：AI提问 → 用户回答 → AI追问/确认 → 用户确认 → 生成卡片。不是一次性生成，是渐进式澄清。

### 2.3 开发执行（OpenHands集成）

待办卡片分析完成后，用户可一键发起开发任务：
- 系统将卡片的结构化内容（背景、目标、技术方案、验收标准）组装为OpenHands的任务上下文
- OpenHands执行开发任务
- 执行过程中的关键节点（方案选择、遇到的问题、最终实现）回写到待办卡片的执行日志
- 用户可在界面上查看执行进度和结果

**人工检验点**：
- 执行前：用户确认AI生成的技术方案
- 执行中：关键决策点暂停等待用户确认（可配置）
- 执行后：用户验收执行结果，标记通过/打回

### 2.4 结构化经验提取与复用

**这是Arc区别于普通待办工具的核心差异点。**

待办完成后，AI自动从待办卡片和执行日志中提取结构化经验卡片：

| 字段 | 说明 | 来源 |
|------|------|------|
| 问题描述 | 这个待办解决了什么问题 | AI从待办卡片提取 |
| 解决方案 | 最终采用了什么方案 | AI从技术方案+执行日志提取 |
| 关键决策 | 过程中做了哪些取舍，为什么 | AI从执行日志提取 |
| 踩坑记录 | 遇到了什么问题，怎么解决的 | AI从执行日志提取 |
| 适用场景 | 这个经验在什么场景下可复用 | AI推断 + 用户确认 |
| 标签 | 技术领域、业务领域分类 | AI生成 + 用户编辑 |

**经验提取流程**：
1. 待办标记完成时，AI自动分析待办卡片全部内容（需求、方案、执行日志、验收结果）
2. 生成经验卡片草稿，展示给用户
3. 用户审核、修改、确认——确保经验质量由人把关
4. 确认后入库，建立与待办卡片的关联

**经验复用机制**：
- 新建待办时，AI通过语义检索匹配历史相关经验，主动推荐
- 需求分析阶段，AI参考相关经验提出更有针对性的澄清问题
- 技术方案生成时，AI将相关经验作为参考上下文注入，避免重复踩坑
- 支持按标签、关键词、适用场景搜索经验库

**技术实现**：使用PostgreSQL + pgvector做语义向量检索，不引入图数据库。经验之间的关联通过标签和语义相似度建立，不做显式的图谱结构——在数据量足够大之前，图谱的维护成本远大于收益。

## 3. 不在第一版范围

- 显式知识图谱（用标签+语义检索替代，数据量不够时图谱是过度设计）
- 多用户 / 团队协作
- 云端部署 / SaaS化
- 项目管理功能（甘特图、冲刺看板等）
- 代码仓库管理

## 4. 技术架构

```
┌─────────────────────────────────────────┐
│              前端 (React + TS)           │
│  待办看板 / 卡片详情 / AI对话 / 执行监控   │
└──────────────────┬──────────────────────┘
                   │ REST API
┌──────────────────┴──────────────────────┐
│            后端 (Python + FastAPI)        │
│                                          │
│  ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐ │
│  │待办管理 │ │AI分析  │ │执行管理 │ │经验提取 │ │
│  │Service │ │Service │ │Service │ │Service │ │
│  └────────┘ └────────┘ └────────┘ └────────┘ │
│                                          │
│  ┌──────────────────────────────────┐    │
│  │     LLM适配层 (多模型切换)        │    │
│  │  Claude / GPT / DeepSeek / ...   │    │
│  └──────────────────────────────────┘    │
│                                          │
│  ┌──────────────────────────────────┐    │
│  │   OpenHands 集成层                │    │
│  └──────────────────────────────────┘    │
└──────────────────┬──────────────────────┘
                   │
         ┌─────────┴─────────┐
         │   PostgreSQL      │
         │  + pgvector       │
         │  待办/经验/日志/配置 │
         └───────────────────┘
```

**技术选型理由**：
- **前端React + TS**：生态成熟，AI编程工具支持最好
- **后端Python + FastAPI**：OpenHands是Python生态，大模型SDK Python支持最好，集成成本最低
- **PostgreSQL + pgvector**：全文检索 + 向量语义检索，支撑经验匹配；后续商业化扩展性强

### 4.1 上下文感知引擎

Arc的核心竞争力不只是"每个环节有AI"，而是"AI在每个环节都知道完整的上下文"。

**上下文编排策略**——每个环节的AI调用，自动注入以下上下文：

| 环节 | 注入的上下文 |
|------|-------------|
| 需求澄清 | 用户输入 + 语义匹配的历史经验卡片 + 关联待办的信息 |
| 技术方案生成 | 待办卡片全部字段 + 匹配的历史经验（尤其是踩坑记录和方案决策） |
| 开发执行 | 待办卡片 + 技术方案 + 相关经验 + 项目代码上下文 |
| 经验提取 | 待办卡片全生命周期数据（需求→方案→执行日志→验收结果） |
| 经验复用 | 当前待办描述 → 语义检索经验库 → 按相关性排序注入 |

**上下文管理机制**：
- 每个待办卡片维护一个上下文链（context chain），记录从创建到完成的全部结构化数据
- AI调用时由上下文编排器（Context Orchestrator）根据当前环节自动组装prompt
- 上下文有优先级——直接关联的经验 > 同标签的经验 > 语义相似的经验，避免上下文过长导致噪音

### 4.2 经验数据模型（面向后续版本扩展）

第一版经验卡片的数据结构需要为后续版本预留扩展能力：

```
经验卡片 (Experience)
├── id
├── 问题描述 (problem)
├── 解决方案 (solution)
├── 关键决策 (decisions[])          ← 结构化数组，每条决策有"选项/选择/原因"
├── 踩坑记录 (pitfalls[])           ← 结构化数组，每条有"问题/原因/解决方式"
├── 适用场景 (applicable_scenarios)
├── 标签 (tags[])
├── 语义向量 (embedding)            ← pgvector，用于语义检索
├── 来源待办ID (source_todo_id)
├── 关联经验IDs (related_experience_ids[])  ← v1通过语义相似度自动关联
├── 置信度 (confidence)             ← 经验被复用后的反馈评分，v2用于排序优化
├── 复用次数 (reuse_count)          ← 追踪哪些经验真正有价值
├── 元数据 (metadata)               ← 预留JSON字段，v2+可扩展为图谱节点属性
└── 创建/更新时间
```

**为后续版本预留的扩展点**：
- `related_experience_ids` → v2可升级为带权重的关系边（图谱化）
- `metadata` → v2可存储领域本体、因果关系等图谱属性
- `confidence` + `reuse_count` → v2可做经验质量自动评估和淘汰
- 经验卡片本身的结构足够原子化，后续可作为图谱节点直接迁移

## 5. 核心用户流程

```
用户输入粗略需求
      │
      ▼
AI多轮澄清对话 ──→ 用户回答/确认
      │
      ▼
生成结构化待办卡片
      │
      ▼
用户确认技术方案 ←── AI生成技术方案
      │
      ▼
一键发起OpenHands开发任务
      │
      ▼
执行过程回写到待办卡片
      │
      ▼
用户验收 ──→ 通过：标记完成，进入经验库
      │         失败：AI分析原因，生成修复待办
      ▼
下次新建待办时，自动关联相似历史经验
```

## 6. 第一版验收标准

1. 能创建、编辑、查看待办卡片，状态能正确流转
2. 输入粗略需求后，AI能通过多轮对话完成需求澄清并生成结构化卡片
3. 能将待办卡片的上下文发送给OpenHands并启动开发任务
4. OpenHands的执行日志能回写到待办卡片
5. 待办完成后，AI能自动生成结构化经验卡片，用户可审核确认
6. 新建待办时，系统能语义匹配历史经验并展示给用户
7. AI在需求分析和方案生成环节能自动引用相关历史经验作为参考
8. 全流程本地可运行
