## 版本目标

把 Arc 自己的迭代治理体系作为"基因"传给交付出的每个项目, 闭环"上下文不断裂"承诺。Arc 帮用户构建项目, 这些项目自身也需要治理规范 (版本迭代/质量门禁/上下文加载)——不传则交付即腐烂。这是"不同项目类型落地"终局第五步: 构建 → 签名 → 分发 → **治理规范传递**。

## 版本验证标准

1. 新建项目时自动产出 project_charter (项目宪章, 按 ProjectType 生成)
2. CONVENTION_TEMPLATES 注册表 (ProjectType → 意图驱动规范模板)
3. 两层传递: 规范文本 + agent 维护规范的自运转能力
4. 不同 ProjectType 生成不同规范 (官网=SEO/PWA/性能, 客户端=签名/分发/跨平台)

## 版本范围

**做什么:**
- project_charter artifact (项目初始化时产出, 等价 CLAUDE.md 但按 ProjectType 生成)
- CONVENTION_TEMPLATES 注册表 (复用 v5.9.0 注册点模式, 与 PROTOTYPE_BUILD_GUIDES/get_deployer/get_distributor 同构)
- 规范模板意图驱动化 (非 Arc 现有规则执行式)
- 两层传递: ① 规范文本 ② agent 维护规范行为 (版本切换/质量检测自运转)

**不做什么:**
- prompt-upgrade-plan 剩余 7 处 → 独立推进 (本版本依赖其完成情况, 可并行)
- v6.0 波次2/3 (web/android 镜像) → 独立推进

## 各任务实施要点

### T1 — project_charter artifact
- 新 artifact: project_charter (项目宪章, 创建项目时初始化)
- 等价 CLAUDE.md 但按 ProjectType 生成 (Arc 自身 CLAUDE.md 是全局, 交付项目 charter 按类型裁剪)
- 复用 artifact 体系 (与 domain_model/convention 同层)

### T2 — CONVENTION_TEMPLATES 注册表
- `CONVENTION_TEMPLATES: dict[ProjectType, str]` — key=ProjectType, value=规范模板
- 复用 v5.9.0 注册点模式 (六处注册点之一, 与 PROTOTYPE_BUILD_GUIDES 同构)
- 规范模板**必须意图驱动格式** (目标+输出契约+上下文), 非 Arc 现有规则执行式 ("文件<500行/必须auth"等硬规则)
- 按类型裁剪: 官网=SEO/PWA/性能规范, 客户端=签名/分发/跨平台规范 (复用 v6.0-v6.2 成果)

### T3 — 两层传递
- ① 规范文本: project_charter 初始化产出 (T1)
- ② agent 维护规范行为: 交付项目内的 agent 能自运转版本切换/质量检测 (只传文本不传机制则文本交付即腐烂)
- 机制传递: 把 Arc 的 docs/versions/ 协议 + current.md 上下文加载 + 任务依赖表 + 质量门禁 简化为可交付版本

## 对后续版本的约束

- 规范模板必须意图驱动化 (不能复制 Arc 现有规则执行式 CLAUDE.md, 待 prompt-upgrade-plan 稳定范式)
- 规范按 ProjectType 裁剪 (官网套重型 DDD 规范是负担, 不是越多越好)
- 复用 v5.9.0 注册点模式 (禁止新造注册机制)
- 依赖 prompt-upgrade-plan (P0/P1/P2 分版本推进) 完成情况决定本版本何时启动
