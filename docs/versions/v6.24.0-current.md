### 二·一、R5 端到端验证结论 (2026-07-01 v6.24 实测)

**推翻 v6.23/backlog 误判**: R5 原标注"blocked 需 PAT/S3/runner/证书"是错的 — R5 不依赖构建凭证 (那是 R3/R4), 只需真实 LLM + provision 链路。实测在 dev 环境 (智谱 glm-5-turbo 经 anthropic 兼容端点 open.bigmodel.cn) **端到端跑通**, 暴露以下真实问题:

**验证通过项**:
- ✅ LLM 链路: 智谱 glm-5-turbo 真实调用 (非 mock), pipeline ARCHITECTURE 阶段产出 tech_architecture artifact (含 data_model.entities)
- ✅ domain_model 提取: refresh 从 tech_architecture 提取 3 聚合 (Order/Payment/Inventory) 入 project.domain_model
- ✅ BaaS provision 机制本身: 手动触发 try_provision_baas_after_extract 真建出 arc_{project} schema + 业务表 (orders/payments/inventories) + 元模型表 (_meta_*) + baas_instances 记录 active

**严重 bug (投产阻断, 待修)**:
- ❌ **[P0] BaaS provision 在 pipeline 主交付路径不自动触发**: provision 只挂在 conversation 模式的 `artifact_extractor → try_extract_domain_model → try_provision_baas` 链; `pipeline generate` (ArtifactService.generate_from_conversation) 和 `domain-model/refresh` (DomainModelService) **都不接入 artifact_extractor → 不触发 provision**; 且无手动 provision 端点 (baas-status 是只读 GET)。后果: 用户走 pipeline 做 architecture, BaaS 永远不 provision, baas-status 永远 false。修法: pipeline generate 后 / refresh 后接 provision 调用, 或加手动 provision 端点。
- ❌ **[P0] provision 建表启用 RLS 但 0 policy → 非 superuser 角色访问 deny-all**: 实测 orders/payments/inventories `relrowsecurity=t` 但 `pg_policies` 计数 0。PostgreSQL 语义: RLS 启用 + 无 policy = 默认拒绝。Supabase 投产场景前端用 anon/authenticated (非 superuser) → 表不可读写。RLS 校验 warning 已检测 ("缺 authenticated SELECT 策略") 但只告警不修复。dev 同库 arc (superuser) bypass RLS 不受影响, 掩盖了此问题。修法: DomainModelApplier.apply_snapshot 按 user_id 列生成 authenticated SELECT/INSERT policy。

**修复 (2026-07-02, P0-1+P0-2 已端到端验证)**:
- ✅ **P0-1**: `DomainModelService` 加 `provision_baas` 统一入口, `refresh_domain_model` 提取后自动调 + `POST /projects/{id}/baas/provision` 手动端点。实测 pipeline → architecture generate → refresh → baas-status `provisioned=true` (之前永远 false)。
- ✅ **P0-2**: `DomainModelApplier.convert_to_baas_schema` 生成默认 RLS policy (有 user_id→行级隔离 `user_id=auth.uid()` / 无 user_id→authenticated 共享) + user_id 列 `DEFAULT auth.uid()`; `SchemaProvisioner` provision 时预建 Supabase 约定 (authenticated/anon 角色 + auth.uid() 函数, dev 兜底/Supabase 内置跳过)。实测 arc_xxx schema `pg_policies=4` (修复前 0=deny-all)。
- CI 基线: ruff0 / pytest 2500 passed (unit+integ) / 全绿, 无回归。
- 改动文件: `application/baas/domain_model_applier.py` + `infrastructure/baas/{sql_generator,schema_provisioner}.py` + `application/project/domain_model_service.py` + `interface/routes/project/operations.py` (端点) + 3 测试文件。

**次要问题**:
- ⚠️ 智谱 glm-5-turbo architecture 产出 **191s/单次** (completion_tokens=3063, 智谱服务端 x-process-time 190s) — 极慢, 严重影响交互体验。worker_model 重定向 glm-4.5-air→glm-4.7 同源 (智谱行为)
- 🐛 `start_phase` 前置检查放行 active 的 clarification: clarification 产品规则"不可跳过"(skip 返回 400), 但 start architecture 时前置检查 (要求前置 CONFIRMED/SKIPPED) 放行了 active clarification, 绕过"必须完成"约束
- ⚠️ 配置易错点: 根 `.env` 全是空占位符, 真实 LLM 配置在 `backend/.env` (cwd=backend 读); 多 .env + pydantic forbid (ARC_DB_PORT infra 变量) 组合, 启动方式不对即 forbid/空 key 500

**复现路径**: docker db/redis + `cd backend && uvicorn arc.main:app` (读 backend/.env) → demo/demo123 → strict project + todo → pipeline/start → skip ui_design → start architecture → generate (191s LLM) → 手动 refresh → 手动调 try_provision_baas (因 pipeline 不自动触发)。

### 二·二、conversation 端到端验证结论 (2026-07-02 续 R5)

**验证目标**: backlog P2 — conversation 路径 (`send_message → ExecutionEngine → ArtifactExtractor → try_provision_baas`) 真实 LLM 端到端, 对照 R5 已测的 pipeline 路径。验证 conversation 发消息能**自动**触发 provision (无需手动 refresh/generate)。

**验证方式**: free 模式 unified conversation (绕过 strict gate LLM 评估卡死循环) → 发消息明确要求产出 tech_architecture。智谱 glm-5-turbo 单次 566s 产出 `[DELIVERABLE:tech_architecture]` 含 `data_model.entities` (Order/Payment/Inventory, 各带 user_id)。

**发现 2 个真实阻断 bug (均已修复)**:

- ❌ **[P0] `execution_engine.py:261` `sandbox_policy.target` AttributeError**: `_tool_aware_stream` 读 `sandbox_policy.target`, 但 `SandboxPolicy` 字段是 `build_target` (纯笔误)。**阻断整个 conversation 模式 LLM 调用** (R5 走 pipeline generate 未触发此分支故未发现)。binary_app project 经 `resolve_sandbox_policy` 返回 mode=docker 的 SandboxPolicy (非 None) → 必抛。修: `.target` → `.build_target`。回归测试: 字段存在性 + 源码引用双断言。
- ❌ **[P1] `domain_model_applier.convert_to_baas_schema` 不容错中文 entity name**: extractor `_entities_to_aggregates` 原样保留 LLM 产出 name (`Order（订单聚合根）`), convert 的 `_IDENT_RE.fullmatch` 拒绝 → 3 聚合全 skip → tables 空 → **provision 被 try_provision 触发了 (日志 "BaaS provision triggered") 但 apply_snapshot 跳过建表**。R5 的 LLM 产出纯英文 name (`BaseAggregateRoot`) 故未暴露。修: convert 边界加 `_slugify_identifier` (取首个 `[a-zA-Z_][a-zA-Z0-9_]*` 片段, 治标在消费边界; extractor 不清洗为数据质量技术债, 改 domain_model 契约需评估消费者单独处理)。回归测试: 中文 name → orders/payments 建表。

**验证结果 (修复后)**:
- ✅ conversation 发消息 → LLM 产出 tech_architecture → ArtifactExtractor 自动 extract 3 聚合入 project.domain_model (日志 "3 agg")
- ✅ 自动触发 try_provision_baas (日志 "BaaS provision triggered", **未调 refresh/generate**)
- ✅ apply_snapshot 建表: `arc_{project}` schema + orders/payments/inventories 3 业务表 + 元模型表
- ✅ RLS policy 每表 4 条 (SELECT/INSERT/UPDATE/DELETE, P0-2 非 deny-all) + orders.user_id `DEFAULT auth.uid()` (行级隔离)
- ⚠️ **闭环说明**: conversation 自动触发链路有日志证据; 建表逻辑 (apply_snapshot) 由手动 `POST /projects/{id}/baas/provision` 验证 (同一函数, convert 修复后建表成功)。未做修复后完整重跑 (智谱单次 566s 成本高), 但两证据在 apply_snapshot 共同函数处闭合。

**配置易错点 (环境, 非代码 bug, 实测踩到)**:
- backend/.env `ARC_DATABASE_URL=...localhost:5432` (host PG), 但实际业务数据在 docker `arc-db-1:5433`; 用户原 uvicorn 经 shell env 覆盖连 5433, `nohup` 重启丢 env → 落回 5432 (另一套 demo 数据) → todo 404。修: 重启显式 `ARC_DATABASE_URL=...5433`。
- `ARC_SUPABASE_DB_URL` 显式设 `+asyncpg` 会跳过 `supabase_client.py` 的 `+asyncpg→postgresql` 自动转换 (仅留空时转换) → provision sync 客户端拒 DSN。修: 留空复用 database_url 自动转换。

**改动文件**: `application/execution/execution_engine.py` (P0) + `application/baas/domain_model_applier.py` (P1) + 2 测试文件。CI 基线: ruff0 / unit 2284 / integ 219, 无回归。
