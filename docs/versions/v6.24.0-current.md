- G1-B: template {matching,apply,extraction}Service 复制 G1 A (resolve_for_context + acquire_for_project)

## 关键技术决策 (已定, v6.23 末)

- **C 类注入 adapter (非 llm_config, 非 db)**: gate/validator 是纯函数无 db, 注入 `adapter: LLMAdapter` 保持纯函数 + 零 DB 耦合 + 最易测。调用方 (ExecutionEngine) `async with adapter_pool.acquire_for_project(cfg) as ad: result = await evaluate_gate(..., adapter=ad)`。
- **B 类需穿 db (非单纯复制 G1 A)**: v6.23 末假设"template services 有 db"**经核实不成立** — 3 服务构造均无 db (只 repo/baas_service), 需从 4 调用方穿 db。apply/extraction 是 per-project (方法有 project_id/source_project_id) → 穿 db 后用 resolve_from_project; **matching 是全局模板搜索 (search_matching 无 project_id) → 需定凭证策略 (用户默认 resolve_default_config vs 保留 env)**。

## 各任务实施要点

### G1-B (template services) — 需穿 db + matching 决策
- 3 服务构造加 db (或方法接 db); 4 调用方 (routes/template.py / context/providers/template.py / project/service.py) 传 db — 这些调用方均有 db (route 的 DbSession / provider 的 project context / project/service 的 db)。
- apply_service.apply (有 project_id) / extraction_service.extract_template (有 source_project_id) → `resolve_from_project`; extraction 2 站点 (L159 title_desc / L243 embedding) 都收口。
- **matching_service.search_matching (无 project_id)**: 决策 — (a) 穿 user_id 用 resolve_default_config (用户默认凭证); (b) 保留 env (全局 op, env 即全局配置)。倾向 (a) 与 G1 A 一致 per-user, 但 matching 无 user_id 需从调用方穿。
- TDD: mock acquire_for_project 验证透传 llm_config (同 G1 A 测试范式)。

### G1-C (gate/validator 注入) — 干净, 推荐先做
- 5 纯函数加 `adapter: LLMAdapter` 必填参数 (**不兜底**, 强制注入消除散落); 内部 `create_resilient_adapter()` 删除, 直接用传入 adapter。
- 调用方排查 + 透传: `evaluate_gate` ← pipeline/service._evaluate_phase_gate (PipelineService 有 db, acquire_for_project); `evaluate_conversation_gate`/`evaluate_sufficiency_gate`/`validate_domain_model`/`llm_review` ← execution engine (ExecutionEngine 已持 _llm_config, acquire_for_project 后传)。
- analysis_service L160 fallback: L144/146/153/155 已用 project config, L160 是无 project env 兜底 → 收口为注入或保留 env (视调用方是否总有 project)。
- TDD: 每个纯函数单测改传入 fake adapter (零 mock create_resilient_adapter)。
