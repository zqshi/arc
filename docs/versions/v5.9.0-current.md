# v5.9.0 Current — 项目类型框架 + 静态站点型落地

> 状态: 进行中
> 起始 commit: c485120 (2026-06-24)
> 上一版本: [v5.8.0](v5.8.0-snapshot.md)

## 版本目标

Arc 当前交付链路是**单类型硬编码**——隐式假设"所有项目 = React SPA → npm run build → dist → S3 静态站点"（`DeployType` 只有 `STATIC_SITE`、`Project` 无 `project_type`、prompt 写死 Vite+React）。本版本把"项目类型"建成 domain 一等公民 + 部署器多态框架，并以静态站点型(官网)端到端落地验证框架可用。

这是"支持不同项目类型落地"多版本路线的**第一步**（框架地基）。终局覆盖原生客户端的构建+签名+商店分发，详见下方全路线总览与 backlog。

## 版本验证标准

1. 用 Arc 创建一个 `project_type=static_site` 的"官网"项目，走完到 DEPLOYMENT 阶段，生成的 dist 上传 S3，`deploy_url` 可访问
2. `DeployService.deploy(project_type=...)` 能按类型路由到对应部署器（单元测试验证选型）
3. 新增项目类型时，只需在 `ProjectType` 枚举 + `get_deployer` 工厂 + `PROTOTYPE_BUILD_GUIDES` 三处注册，无需改链路分支

## 版本范围

**做什么:**
- domain: `ProjectType` 枚举 + `Project` 实体字段 + `DeployConfig.for_type()` 工厂
- 部署器多态: `Deployer` 抽象基类 + `get_deployer` 工厂（`StaticSiteDeployer` 重构为 STATIC_SITE 实例）
- `DeployService.deploy()` 按 type 路由；`deploy_static_site()` 保留为薄封装兼容现有调用点
- prompt 按 `project_type` 参数化（`PROTOTYPE_BUILD_GUIDES`）
- 接口层 + 前端: schema/route/service 加 `project_type`；创建表单加选择器
- ORM + migration: `projects` 表加 `project_type` 列

**不做什么:**
- `BINARY_APP` 等非 STATIC_SITE 类型的 deployer 实现 → v6.0.0
- `DockerSandboxRuntime` 真实现（当前 `raise NotImplementedError`）→ v6.0.0
- 签名/公证 → v6.1.0（凭证可配置，非阻塞）
- 商店分发 + 二进制制品分发层 → v6.2.0

## 各任务实施要点

### T2 — domain: ProjectType
- `ProjectType(StrEnum)`: 本版本仅 `STATIC_SITE="static_site"` 实质值；预留注释 `BINARY_APP/BACKEND_SERVICE/CONTAINER/LIBRARY`（后续激活时再加，避免死代码检测）
- 与现有 `backend_type`(none/supabase/embedded/external)、`app_code.framework`(react/vue/...) **正交**
- `Project.project_type` 默认 `STATIC_SITE`
- `DeployConfig.for_type(project_type)`: STATIC_SITE → `build_command="npm run build"`, `artifact_path="dist"`

### T3 — 部署器多态
- `base.py`: 抽象基类 `Deployer`（`deploy(*, local_dir, project_id, deploy_id) -> DeployResult`）+ `DeployResult` 从 `static_site.py` 上移
- `StaticSiteDeployer(Deployer)`: 行为不变（纯重构）
- `get_deployer(deploy_type) -> Deployer`: STATIC_SITE → StaticSiteDeployer

### T4 — DeployService 路由
- `deploy(*, project_type, ...)`: 经 `get_deployer()` 选 deployer，`Deployment.deploy_type` 由 type 决定
- `deploy_static_site()`: 改为 `return await self.deploy(project_type=ProjectType.STATIC_SITE, ...)`，保留兼容 `hooks.py:130` + `artifact_deployer.py:155`

### T5 — prompt 参数化
- `prompts.py:179-232` 原型工程化指导 → 抽 `PROTOTYPE_BUILD_GUIDES: dict[str, str]`，按 `project.project_type` 注入
- `prompt_builder` project provider 注入 `project_type`
- `artifact_deployer.py:155` 调用点改 `deploy(project_type=...)`

### T6 — 接口层 + 前端
- `ProjectCreate/Update/Response` 加 `project_type: Literal["static_site"] = "static_site"`
- `core.py:37 create_project` 透传
- 前端创建表单加选择器（STATIC_SITE 默认且唯一可选，UI 预留）；`api.ts` 类型同步；提交前 `tsc --noEmit`

### T7 — ORM + migration
- `ProjectModel.project_type: Mapped[str] = mapped_column(String(30), default="static_site", server_default="static_site")`
- alembic migration: `projects` 加列，`server_default='static_site'` 存量回填

## 对后续版本的约束

- `ProjectType` 是新增正交维度，后续类型必须在 `ProjectType` + `get_deployer` + `PROTOTYPE_BUILD_GUIDES` 三处注册，禁止在 service/prompt 里加 `if project_type` 分支
- 凭证配置项在 v6.1.0 引入时必须同步 `.env.example`（配置一致性 6.3）
- v6.0.0 激活 BINARY_APP 时，本版本预留的扩展点直接复用，无需改框架
