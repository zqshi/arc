# v5.6.0 — BaaS 运行时层（Supabase 全接入）

> **主题**: 引入 Supabase BaaS，让 Arc 生成的应用具备真实后端（数据库+权限+API+Action）
> **前置**: v5.5.0 完成（DEVELOPMENT 补全 + SERVICE_SPEC 锚点就绪）
> **参考**: XSpace `feat_agent_native_app.md` 架构 + `supabase/provisioner.py` 实现
> **依赖 v5.5.0**: 本版本接入基于 v5.5.0 的 `SERVICE_SPEC.data_persistence="supabase"` 与 `APP_CODE` artifact，把 SERVICE_SPEC 的 `supabase` 值从"声明但拒绝执行"升级为"声明并真实 provision"

---

## 版本目标

1. 引入 Supabase 作为 BaaS 可信内核（PG + RLS + PostgREST + Edge Function）
2. 新建 `domain/baas/` 聚合：定义 BaaS Schema、Table、RLS Policy、Action 的领域规则
3. 将现有 DomainModelSnapshot **可执行化**：领域模型→ SQL 生成 → 真实建库
4. ARCHITECTURE 阶段产出领域模型后，自动 provision Supabase schema
5. DEVELOPMENT 阶段：前端直连 PostgREST、Action 逻辑落 Edge Function
6. Agent Tool 升级：`supabase_provision`, `supabase_execute_sql`, `get_domain_model`

## 关键决策

### 1. Supabase 部署拓扑

| 环境 | 方案 | 说明 |
|------|------|------|
| 开发/自部署 | Docker Compose 起 Supabase 全家桶 | `supabase start` 本地起完整环境 |
| 生产 | Supabase Cloud 或自建 K8s Supabase | 通过 Management API 创建项目 |

**每个 Arc Project 对应一个 Supabase schema**（不是独立数据库），复用 XSpace 验证过的 `app_{id}` schema 隔离方案。

### 2. 与现有 DomainModelService 的整合

```
当前: DomainModelSnapshot (dict) → 存为 project.domain_model (JSONB)
升级后:
  DomainModelSnapshot (dict) 
    → DomainModelApplier.apply(snapshot, supabase_client)
      → CREATE TABLE / ALTER TABLE
      → INSERT INTO _meta_entities
      → CREATE POLICY
      → CREATE/REPLACE FUNCTION (Edge Function)
```

关键改动：`DomainModelSnapshot.content` 的结构需规范化——当前是 `{subdomains, contexts, aggregates, relations}`，需要扩展为可映射到 SQL 的精确 schema。

### 3. 元模型表设计（借鉴 XSpace `_meta_*`）

每个 Arc Project 的 Supabase schema 内自动创建：

```sql
-- 实体元数据
CREATE TABLE _meta_entities (
  name TEXT PRIMARY KEY,
  description TEXT,
  has_state_machine BOOLEAN DEFAULT false,
  created_at TIMESTAMPTZ DEFAULT now()
);

-- 状态定义
CREATE TABLE _meta_states (
  entity_name TEXT REFERENCES _meta_entities(name),
  state TEXT,
  description TEXT,
  is_initial BOOLEAN DEFAULT false,
  is_terminal BOOLEAN DEFAULT false,
  PRIMARY KEY (entity_name, state)
);

-- 跃迁定义
CREATE TABLE _meta_transitions (
  entity_name TEXT,
  from_state TEXT,
  to_state TEXT,
  action_name TEXT NOT NULL,
  guard_description TEXT,
  PRIMARY KEY (entity_name, from_state, to_state)
);

-- 权限声明
CREATE TABLE _meta_policies (
  table_name TEXT,
  operation TEXT,  -- SELECT/INSERT/UPDATE/DELETE
  role TEXT,       -- authenticated/anon/service_role
  condition TEXT,  -- SQL 表达式
  PRIMARY KEY (table_name, operation, role)
);
```

Agent 通过 `get_domain_model` tool 读取这些元表，了解当前应用的领域结构后再做增量变更。

### 4. 认证集成

Arc 已有 JWT auth 体系。生成的应用使用：

- **平台 JWT → Supabase 兼容 JWT 转换**：Arc auth 签发的 token 中加入 `schema` claim
- PostgREST 用 `request.jwt.claims->>'schema'` 切 search_path
- 不引入 GoTrue 做应用层 auth——Arc 统一 auth 层直接签发 Supabase 兼容 token

### 5. Action 机制（业务合法性保障）

RLS 只管"谁能访问"，Action 管"这次操作是否合法"：

```
前端点击 → 调用 Edge Function (action) → 校验前置条件 → 执行写入 → Trigger 审计
```

Agent 在 DEVELOPMENT 阶段自动生成：
- 关键状态跃迁对应的 Edge Function
- 通用审计 Trigger（`updated_at` + event log）

## 领域模型设计

### BaaS 聚合 (domain/baas/)

```python
# domain/baas/value_objects.py

@dataclass(frozen=True)
class ColumnDef:
    name: str
    type: str  # "uuid", "text", "int", "timestamptz", "boolean", "jsonb"
    nullable: bool = True
    default: str | None = None  # "auth.uid()", "now()", etc.
    is_primary: bool = False
    references: str | None = None  # "other_table(id)"

@dataclass(frozen=True)
class TableDef:
    name: str
    columns: list[ColumnDef]
    has_rls: bool = True
    has_state_machine: bool = False
    state_field: str | None = None  # 状态字段名

@dataclass(frozen=True)
class RlsPolicy:
    table_name: str
    operation: str  # SELECT/INSERT/UPDATE/DELETE
    role: str  # authenticated/anon
    using_expr: str | None = None  # WHERE condition for SELECT/UPDATE/DELETE
    check_expr: str | None = None  # WITH CHECK for INSERT/UPDATE

@dataclass(frozen=True)
class StateTransition:
    entity: str
    from_state: str
    to_state: str
    action_name: str
    guard: str  # SQL-like 前置条件描述

@dataclass(frozen=True)
class ActionDef:
    """业务动作定义 → 生成 Edge Function。"""
    name: str
    entity: str
    transition: StateTransition | None
    preconditions: list[str]  # 自然语言描述的前置条件
    effects: list[str]  # 写入的副作用
    is_idempotent: bool = False

@dataclass(frozen=True)
class BaasSchema:
    """一个项目的完整 BaaS Schema 定义。"""
    schema_name: str  # "arc_{project_id_short}"
    tables: list[TableDef]
    policies: list[RlsPolicy]
    transitions: list[StateTransition]
    actions: list[ActionDef]
```

### BaaS 追踪实体

```python
# domain/baas/entity.py

@dataclass
class BaasInstance:
    """追踪项目与 Supabase 实例的绑定关系。"""
    id: UUID
    project_id: UUID
    schema_name: str
    supabase_url: str  # PostgREST endpoint
    status: BaasStatus  # provisioning/active/suspended/deleted
    last_applied_model_version: int  # 对应 DomainModelSnapshot.version
    created_at: datetime
    
    def provision(self) -> None: ...
    def activate(self) -> None: ...
    def apply_model(self, version: int) -> None: ...
    def suspend(self) -> None: ...
```

## 验收标准

1. ✅ 新项目创建 + ARCHITECTURE 阶段完成后，Supabase 中自动创建对应 schema + 元模型表
2. ✅ Agent 通过 `supabase_execute_sql` tool 能建表、写 RLS、读元模型
3. ✅ 生成的前端能通过 PostgREST 直连 Supabase 读写数据
4. ✅ 状态机跃迁有对应 Edge Function，前端调用 Action 能完成业务流转
5. ✅ DomainModelSnapshot 版本 N → N+1 时，增量 SQL 正确应用（不破坏现有数据）
6. ✅ RLS 校验覆盖 XSpace 的 5 项关键检查（user_id DEFAULT、ENABLE RLS、INSERT TO authenticated 等）

## 约束与风险

- **Supabase 环境强依赖**: 本版本开发需要本地起 Supabase（`supabase start`），CI 需要对应 service。开发环境配置成本上升。
- **DomainModelSnapshot 结构变更**: 需要兼容存量数据——旧格式（`{subdomains, aggregates}`）应能 graceful fallback（不 apply 到 Supabase，仅保持文档态）。
- **增量 DDL 风险**: 模型版本 N→N+1 的 ALTER TABLE 可能丢数据。需要 `sql_generator` 输出 migration-style SQL（不允许 DROP COLUMN，只允许 ADD/RENAME），并要求人工确认破坏性变更。
- **RLS 泄漏风险**: Agent 生成的 RLS 可能有漏洞。`rls_validator.py` 必须做 XSpace 级别的校验——但不阻断，只是 WARNING + 人工审批 gate。
