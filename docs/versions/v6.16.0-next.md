## 任务详情

### T1 — execution_mode deprecated 字段下线

**问题**: todo/project 仍有 deprecated `execution_mode` (entity 默认 PIPELINE), 与 `process_constraint` (默认 FREE) 双源真值。前端 `UnifiedWorkspaceView.tsx:50` 读 `todo.execution_mode === 'pipeline'` 路由 UI, 后端 todo/crud.py:137-152 从 project 继承 execution_mode。两套字段并存易撕裂 (v6.15 已暴露 create 漏写 bug 的根源之一)。

**做法**:
- 后端: todo entity 加 `process_constraint` 或运行时从 project 查 (v6.15 模式守卫已用运行时查 project 方案, 可复用); 删 entity.execution_mode; alembic drop column
- 前端: UnifiedWorkspaceView 改读 process_constraint; 兼容旧 API 响应 (后端响应可保留 execution_mode 字段为 process_constraint 的镜像, 过渡期)
- 风险: 前后端契约变更, 需协同发布

**为何 P2 而非 P1**: v6.15 模式守卫已用 project.process_constraint 作单一真相源, execution_mode 不影响正确性, 仅是冗余。下线是收敛, 非修复 bug。

### T2 — strict 阈值双存

**问题**: `pipeline/gate.py:147` 硬编码 `if score < 7: passed = False`, 绕过 GateProfile。对话链路 (conversation_gate) 读 `get_profile(constraint).score_threshold`。同一"strict=7"两处各存一份, 巧合相等非同源。

**做法**: pipeline/gate.evaluate_gate 接收 constraint 参数, 改读 `get_profile(constraint).score_threshold`。需确认 evaluate_gate 调用方能传 constraint (目前 `_evaluate_phase_gate` 已有 project_ctx)。

### T3 — DELIVERABLES_BY_CONSTRAINT 死结构

**问题**: `STRICT/MODERATE/FREE_DELIVERABLES` 三档都指向 `REQUIRED_DELIVERABLES` (v6.15 注释已明示"向后兼容")。`conversation_strategy.py:338-358` 的 reorder 因此恒等 (空操作)。

**做法**: 删 `DELIVERABLES_BY_CONSTRAINT` dict + 三档别名, 直接用 `REQUIRED_DELIVERABLES`; 删 conversation_strategy 的 needs_reorder 空逻辑。

### T4 — 测试 DB 隔离缺陷

**问题**: `conftest.py:39` db_session 在 setup 阶段 `commit()` (插 test user), teardown 只 `rollback()`——已 commit 数据回不去。真实共享 PG 跨 run 残留, 导致 test_capability_api 三文件合跑偶发 409 (清 capabilities 表后全绿)。

**做法**: db_session 改用事务回滚隔离 (整个测试在一个事务里, 结束 rollback 全部), 或每个测试前 truncate 相关表。注意: 同 v5.10 test_health 时序污染同类, 可一并根治。

## 对后续版本的约束

- 延续 v6.15 约束: 依赖约束 (DAG) 三档共享硬不变量; ProcessConfig 仅持 constraint; pipeline 写操作受模式守卫保护; ProjectRepository 新增字段同步 create + to_entity。
- T1 (execution_mode 下线) 完成后, process_constraint 成为唯一真相源, 模式守卫可简化 (不再回退 execution_mode 分支)。
