## 各任务实施要点

### D1 — 全局默认凭证接通 DB (关键路径)

**现状边界 (v6.20)**: `create_llm_adapter()` 同步读 config.py env; `create_resilient_adapter()` → `create_llm_adapter()`; `adapter_pool._ensure_adapter(_DEFAULT_KEY)` 同步构造。全局默认走 env, 项目级 llm_provider_id 走 DB。

**核心张力**: `create_llm_adapter()` 同步, 读 DB 凭证需 async session。

**候选方案 (待 D1 评估选定)**:
- **方案 A (adapter_pool 预加载)**: lifespan 启动时 async 读 DB 默认凭证 → 构造 adapter → 注入 `adapter_pool._adapters[_DEFAULT_KEY]`。凭证 CRUD 后清缓存 + 后台重建。`create_llm_adapter()` 保留 env fallback (DB 无凭证时)。改动集中 lifespan + adapter_pool, 调用方零改。
- **方案 B (create_llm_adapter 异步化)**: 改 `create_llm_adapter() → async`, 所有调用方 (todo/service:48, resilience:291) 改 await。彻底但侵入大, 同步/异步边界风险高。

**倾向方案 A** (集中改动, 调用方零侵入, 同 v6.20 决策 "adapter_pool 内存缓存预加载规避全链路 async")。

### T1 — 前端 9 组件超 300 拆分

续11 记: 9 个 .tsx 超 300 行 (CLAUDE.md 6.5 组件拆分线)。逐个抽子组件, 纯结构搬运 JSX 零行为变化 (同 v6.19 续10 ExperienceDetailModal/DomainModelTab 拆分模式)。

### T2 — Project dict 字段值对象化 (评估范围)

续11 P2: Project 实体 dict 字段 (conversation_config/pipeline_config 等) 应显式值对象化。**评估范围**: 部分 dict (如 loop_config) 已有结构, 全量值对象化工作量大; 评估哪些值得做, 哪些 dict 字段保留 (灵活配置场景 dict 更合适)。

### T3 — 聚合边界重构 (评估 DI)

续11 P2 / v6.19 A4 核实: pipeline/hooks.py 跨聚合直接 ProjectRepository(db)/ArtifactRepository(db)。**v6.19 A4 已核实**: 项目无 DI 容器, 函数式 db 参数是全项目统一模式, hooks.py 是纯函数编排片段。**T3 评估**: 是真聚合违规还是既定模式? 若既定模式则跳过 (同 A4 判断), 若违规则改 application service 编排。
