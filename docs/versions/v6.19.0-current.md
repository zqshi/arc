## 版本目标

让 BINARY_APP 项目能构建并签名分发 Windows / iOS / 鸿蒙 原生客户端产物, 对齐已存在的三平台签名器链路。不破坏现有 linux/web/android-apk 三目标, 不改 DDD 领域行为。

## 版本验证标准

1. 新建项目选 BINARY_APP 后, 构建目标下拉可选 Windows / iOS / 鸿蒙 (前端透出)
2. 各平台走通"构建 → 产物建模 → 签名 → 分发"链路 (真实凭证/runner 就绪后端到端验证)
3. 质量检测 6.1-6.7 全过, 现有三目标零回归

## 关键技术约束 (决定方案)

**核心约束: 当前容器化架构无法构建三新平台产物。**

`DockerSandboxRuntime` + Linux builder 镜像 (tauri-builder/web-builder/android-builder) 只能跑 Linux 容器。
- Windows .exe/.msi 需 WebView2 (仅 Windows) → 需 Windows 原生 runner
- iOS .ipa 需 Xcode + xcodebuild → 需 macOS 原生 runner (Docker 在 Linux host 跑不出 iOS 签名产物)
- 鸿蒙 .hap 需 DevEco Command Line Tools → DevEco 工具链容器化支持差, 需原生或专用镜像

tauri-builder.Dockerfile 注释已明记此约束 (v6.0 决策): "macOS .dmg / Windows .exe 需原生 OS, 容器化沙箱无法构建, 推后到原生 runner / CI matrix"。

→ **T1 架构前置** 是三平台共同关键路径: 决定新平台构建走"CI matrix job 产产物 + arc 编排签名" (延续 v6.18 docker-publish.yml builder 镜像发布的 CI 模式) 还是扩展 NativeRunnerRuntime 对接 GHA windows/macos runner。

## 各任务实施要点

### T1 — 原生 runner 执行后端方案选型 (架构前置, 关键路径)

当前 DockerSandboxRuntime 只跑 Linux 容器, 三新平台都需原生 OS runner。决策点:
- **方案 A (CI 编排)**: 构建产物在 GHA matrix job (windows-latest / macos-latest) 产出, arc 运行时只编排 (触发 CI + 轮询产物 + 收集 + 签名), 不直接执行构建。延续 v6.18 docker-publish.yml builder 镜像 CI 模式。
- **方案 B (原生 runtime)**: 扩展 SandboxRuntime ABC 新增 NativeRunnerRuntime, 对接 GHA runner 实时构建。复杂度高, 实时性佳。

建议方案 A (CI 编排): arc 核心是"编排 + 签名 + 分发"而非"实时构建引擎", 且 builder 镜像已走 CI 发布。决策后建 SandboxPolicy 的 target 路由 (新 target 走 CI job 而非 docker runtime)。

### T2/T5/T8 — artifact 显式建模 (每平台第一步, 铁律: 先 artifact 后 runtime)

- T2 Windows: 产物类型 .msi/.exe, 复用已有 SignerType.WINDOWS (v6.1 signtool), 建模 artifact 元数据 + 签名链路声明
- T5 iOS: 产物类型 .ipa, **需新增 SignerType.IOS** (当前 APPLE=mac .app 的 codesign+notarytool, iOS 是 xcrun + provisioning profile + Apple Developer, 流程不同)
- T8 鸿蒙: 产物类型 .hap/.app, **需新增 SignerType.HARMONY** (华为 .p12 + .cer + .profile, 全新流程)

每平台在 `domain/artifact/value_objects.py` + `DELIVERABLES_BY_TYPE` 注册可见产物, 延续 v6.9 按类型裁剪交付物模式。

### T3/T6/T9 — 构建目标 (BuildTarget + builder 镜像/runner + 12 处注册)

- T3 Windows: `BuildTarget.TAURI_WINDOWS` (tauri v2 产 .msi/.exe, WebView2); 需 windows runner 或 mingw 交叉编译 (能产 exe 但运行时验证需 Windows); tauri-builder 现仅 linux, 新增 windows 构建链路
- T6 iOS: `BuildTarget.CAPACITOR_IOS` (与 android 一致走 capacitor, 非 tauri-mobile 实验性); macOS runner + xcodebuild 产 .ipa
- T9 鸿蒙: `BuildTarget.HARMONY_HAP` (DevEco CLT + hvigorw assembleHap); ArkTS/ArkUI 脚手架与现有 react/web 前端正交, 可能需新脚手架适配; 工具链容器化支持差, 倾向原生/专用镜像

### T4/T7/T10 — 签名对接

- T4 Windows: SignerType.WINDOWS (signtool + EV 证书) 已存在 (v6.1), 仅对接构建产物, 对齐 [[project-type-roadmap]] "mac/win 待 Apple Developer ID 证书 / Windows runner"
- T7 iOS: 新增 SignerType.IOS (xcrun + provisioning profile + Apple Developer account), 区别于 mac .app 的 notarytool
- T10 鸿蒙: 新增 SignerType.HARMONY (华为 .p12 + .cer + .profile, hap-sign-tool 或 DevEco signing)

### T11 — 前端透出

`CreateProjectModal.tsx` BUILD_TARGET_OPTIONS 加三新目标卡片 (Windows/iOS/鸿蒙), 透出 requiresDocker 标注 (新平台走 CI runner, 标注与容器构建不同的部署形态提示)。`types/api.ts` BuildTarget 类型同步。
