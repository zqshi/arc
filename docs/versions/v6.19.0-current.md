## 关键技术约束 (决定方案)

**核心约束: 当前容器化架构无法构建三新平台产物。**

`DockerSandboxRuntime` + Linux builder 镜像 (tauri-builder/web-builder/android-builder) 只能跑 Linux 容器。
- Windows .exe/.msi 需 WebView2 (仅 Windows) → 需 Windows 原生 runner
- iOS .ipa 需 Xcode + xcodebuild → 需 macOS 原生 runner (Docker 在 Linux host 跑不出 iOS 签名产物)
- 鸿蒙 .hap 需 DevEco Command Line Tools → DevEco 工具链容器化支持差, 需原生或专用镜像

tauri-builder.Dockerfile 注释已明记此约束 (v6.0 决策): "macOS .dmg / Windows .exe 需原生 OS, 容器化沙箱无法构建, 推后到原生 runner / CI matrix"。

→ **T1 架构前置** 是三平台共同关键路径: 决定新平台构建走"CI matrix job 产产物 + arc 编排签名" (延续 v6.18 docker-publish.yml builder 镜像发布的 CI 模式) 还是扩展 NativeRunnerRuntime 对接 GHA windows/macos runner。

### T1 — 原生 runner 执行后端方案选型 (架构前置, 关键路径) — ✅ done

**裁决: 方案 A (CI 编排), 精确形态如下。**

方案对比 (基于代码事实审视, 非文档转述):
- **方案 A (CI 编排)** ✅: 构建产物在 GHA matrix job (windows-latest/macos-latest) 产出 (upload-artifact), arc 运行时只编排 (触发 workflow_dispatch → 轮询 run → 下载 artifact → 接入 BUILD artifact 锚点), 不直接执行构建。arc 核心是"编排 + 签名 + 分发"而非实时构建引擎。
- **方案 B (原生 runtime)** ✗: 扩展 SandboxRuntime ABC 加 NativeRunnerRuntime。否决理由: `SandboxRuntime` 契约是 `run_command(params)->str` 同步单命令返回输出 (三实现 ApprovalGate/Docker/OpenSandbox 均遵循), GHA runner 是"触发 dispatch→分钟级异步→下载产物"的 batch 语义, 与同步单命令错配; 且 CI 产物是 .msi/.ipa 文件 (走 upload-artifact+下载) 非 stdout 字符串, 返回值类型错配。硬塞会扭曲 v6.18 刚理清的契约。

##### 设计5: source_url S3 presigned 方案

**现状 (storage.py 事实)**: `_is_s3=bool(storage_endpoint):35`; `get_public_url:241` — storage_public_url 存在→`{base}/{key}`, 否则→`{endpoint}/{bucket}/{key}`, 都无→`/static/previews/{key}` (本地, CI 不可达); bucket public GetObject policy (_ensure_bucket:57); **无 presigned URL 能力**。
