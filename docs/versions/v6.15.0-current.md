# v6.15.0 Current — 过程约束依赖守卫治理

> 状态: 进行中 (T1-T3 done — 治理完成, 待补集成测试 + 归档质量检测)
> 起始 commit: 53069df (2026-06-28, v6.14 归档基点)
> 上一版本: [v6.14.0](v6.14.0-snapshot.md)

## 版本目标

审查三模式默认执行逻辑时发现: FREE 模式 soft 放行允许"没需求就开发/没原型就写代码", 且 STRICT 与 FREE 两套顺序逻辑分叉 (STRICT 走 phase 顺序检查, FREE 走 deliverable 依赖检查)。本版本确立设计原则——依赖约束 (DAG) 是三档共享硬不变量, 不该由模式开关决定——并据此修正 DAG、废除 soft 放行、让 STRICT 链路也过 DAG 守卫。

## 版本验证标准

1. app_code 在 prototype 未达标时不可产出 (堵"没原型就写代码")
2. dev_report/test_report 在 app_code 未达标时不可产出 (堵"没代码就报告/测试")
3. 三档 (strict/moderate/free) 缺前置一律硬阻断, 无 soft 放行
4. STRICT skip 阶段后产出依赖未满足 artifact 时被 DAG 拦下
5. ProcessConfig 无死字段, create/update 构造路径一致
6. pipeline 写操作仅 STRICT 可用, FREE/MODERATE → 409; 设置 strict 后 DB 真存 strict
7. pytest unit 全绿 / ruff 0 / 前端 tsc-b 0

## 版本范围

**做什么:**
- T1: DAG 补全 (补 5 条依赖边 + 无环校验)

## 各任务实施要点

### T1 — DAG 补全

`DELIVERABLE_DEPENDENCIES` 补 5 条边:
- `tech_architecture`: +prototype (架构定路由/技术栈须基于原型骨架)
- `app_code`: +prototype (堵"没原型就写代码")
- `dev_report`: +app_code (报告实现须有被实现代码)
- `test_report`: +app_code (测试须有被测代码)
- `experience_card`: [requirement_spec, dev_report] (有实现沉淀即可提炼, 不强制部署; 用户拍板)

build 不入图 (类型裁剪产物, 仅 BINARY_APP, 见 value_objects._BUILD_ONLY)。
加 `test_graph_is_acyclic` 测试锁定无环不变量。

### T2 — 废除 soft 放行

- 删 `GateProfile.dependency_block_mode` / `dependency_hard_block` 两字段
- 删 `ConversationGateResult.dependency_warning` 字段及 to_quality 序列化
- `artifact_extractor._validate_extracted_artifact` 简化: 缺前置一律硬阻断, 删 soft 警告分支
- 依赖约束不再由 constraint 决定, 三档统一硬守卫

### T3 — STRICT 补 DAG 守卫

`_evaluate_phase_gate` 在收集 prior_artifacts 后、调 evaluate_gate 前, 插入 DAG 守卫:
- `missing_prerequisites(artifact.artifact_type.value, prior_artifacts.keys())`
- 缺则返回 `GateResult(passed=False, score=0)`, 由 confirm_phase 抛 PhaseGateError
- 覆盖 skip 阶段缺口: skip 掉 UI_DESIGN 后 confirm ARCHITECTURE, phase 顺序放行 (skipped 算完成) 但 prototype 依赖未满足 → DAG 硬阻断
- DAG 短路时不调 evaluate_gate (省 LLM 成本, 与 FREE short-circuit 一致)

### T4 — ProcessConfig 死字段清理

- 删 `gate_strictness`/`auto_extract`/`require_explicit_confirm`/`show_phase_ui` 四字段 (前后端零业务消费, gate 行为由 GateProfile 接管)
- ProcessConfig 退化为仅持 constraint 的序列化容器; to_dict/from_dict 同步精简
- `from_execution_mode` 成为旧 ExecutionMode 的单一映射点 (PIPELINE→STRICT/否则→FREE), create (from_execution_mode) 与 update (ProcessConfig(constraint=)) 构造路径收敛一致
- 前端 `types/api.ts` ProcessConfig 同步删 4 字段

### T5 — 后端模式守卫 + create 持久化 bug 修复

- pipeline 5 个写操作 (start_pipeline/start_phase/confirm_phase/skip_phase/rollback) 入口接入 `_require_pipeline_mode`: FREE/MODERATE → 409 mode_mismatch
- 真相源: `todo.project_id → project.process_constraint`; 无 project 回退 `todo.execution_mode`
- conversation send_message + 读/artifact 操作不守 (跨模式共享)
- **附带修复**: `ProjectRepository.create` 漏写 process_constraint/process_config (DB 用 ORM default "free" 覆盖)。此 bug 潜伏已久 (之前逻辑都走 execution_mode), 守卫依赖 process_constraint 时暴露。补写后 strict 项目 DB 正确存 strict。存量数据回填见 T6。

### T6 — 历史数据 process_constraint 回填 migration

`z18_backfill_process_constraint` (data migration, down_revision=z17):
- 回填被 bug 污染的存量: `execution_mode='pipeline' AND process_constraint='free'` → `'strict'`
  (只改被污染的 pipeline 项目; conversation 的 free 本就正确不动)
- 规整 process_config 为 T4 格式 `{"constraint": <值>}`, 消除旧 5 字段格式与 NULL 混存
- 实测回填: 959 个 pipeline→free 修正为 strict (14 个 v4 前回填的 + 10 conversation 不变)
- downgrade 为 no-op (数据修正确正, 回退无意义)

## 遗留 (记入后续版本技术债务)

1. **strict 阈值双存** (P2): `pipeline/gate.py:147` 硬编码 `score < 7` 绕过 GateProfile; 应改读 `get_profile(constraint).score_threshold`。
2. **DELIVERABLES_BY_CONSTRAINT 死结构** (P2): 三档 key 指向同一列表, conversation_strategy reorder 实为空操作。建议删 dict 直接用 REQUIRED_DELIVERABLES。
3. **测试 DB 隔离** (P2): `conftest.py:39` db_session setup 阶段 commit() user 注入, teardown 只 rollback() 救不回已提交数据。真实共享 PG 跨 run 残留导致 test_capability_api 三文件合跑偶发 409 (清表后全绿)。建议事务回滚隔离或测试前 truncate。
4. **execution_mode deprecated 字段下线** (P2): 前后端契约仍用 execution_mode (UnifiedWorkspaceView 读 todo.execution_mode==='pipeline'), 与 process_constraint 双源真值未收敛。需独立迁移: 前端改读 process_constraint + 后端删 entity.execution_mode。

## 对后续版本的约束

- 依赖约束 (DAG) 是三档共享硬不变量, 禁止再引入 per-mode 的 dependency_block 开关。
- DAG 是交付物顺序的唯一真相源; STRICT 的 phase 顺序检查与 DAG 守卫职责不同 (前者编排, 后者依赖), 共存不合并。
- 新增交付物类型时必须: (a) 加入 DELIVERABLE_DEPENDENCIES (b) 确保图无环 (test_graph_is_acyclic 守护) (c) 若是类型裁剪产物 (如 build) 走 _BUILD_ONLY 不入核心图。
- ProcessConfig 仅持 constraint, 不再加行为字段 (gate 行为由 GateProfile 接管); 新增过程行为参数应进 GateProfile 而非 ProcessConfig。
- pipeline 写操作受模式守卫保护 (`_require_pipeline_mode`), 新增 STRICT 专属写端点必须接入守卫。
- ProjectRepository 新增持久化字段必须同步在 create 与 _to_entity 两处 (create bug 教训: 漏写则 ORM default 覆盖, entity↔DB 不一致)。
- 延续 v6.9-v6.14 约束。
