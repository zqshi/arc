## 版本目标

激活 v5.9.0 项目类型框架的第二个项目类型 `BINARY_APP`——打通原生客户端（桌面/移动）的容器化构建链路：DockerSandboxRuntime 真正可用 + 二进制构建 + 产物落制品目录。同时落地 prompt-upgrade-plan #7（sufficiency 接线）+ ConstraintPolicy 死配置清理。结束 Arc 只能交付"静态站点"的单类型局限，向"不同项目类型落地"终局迈出第二步。

构建链路真相：构建不走 DeployService 直接执行 build_command（它只接收已完成的 local_dir 做上传），真实构建 = Agent 在执行循环里调 run_command → 经 DockerSandboxRuntime → docker run。故本版本核心 = **让 DockerSandboxRuntime 用对镜像 + BINARY_APP 自动启用容器化**。

## 关键决策

- **三目标按波次拆分**: current.md 原验证标准要求 linux/web/apk 三目标,但内在矛盾(web 接近 STATIC_SITE 重复、android apk 用 tauri 逆流、tauri linux 最低频)。决策: 三目标都进 v6.0 范围但拆 3 波次,架构层一次做对,波次2/3 只填注册表+激活枚举值。**迭代的是镜像内容与验证,不是架构欠债**
- **BuildTarget 维度一次引入**: domain 层 BuildTarget 枚举(TAURI_LINUX 激活, WEB/CAPACITOR_APK 预留注释避免死代码检测)。镜像推导 (project_type, build_target)→image 二维决策,波次2/3 零架构返工
- **镜像推导在 application 层, runtime 零改**: policy_resolver 解析策略填入 SandboxPolicy.docker_image,SandboxPolicy 不耦合 project_type(保持"已解析最终配置"职责)。既有 12 项真实 docker 测试不受影响
- **自建多工具链镜像**: 官方无现成 tauri 镜像(需 webkit2gtk 系统依赖),必须自建 arc/tauri-builder:linux
- **BINARY_APP 自动启用容器化**: 原生客户端构建依赖工具链镜像,宿主直跑必失败,故默认注入 mode=docker(无需用户手动配 sandbox)
- **sufficiency 产出前门禁**: 用户确认方案,非原推荐 A+B 轮次预筛+缓存。职责分离:轮次管引导,LLM 管质量判断
- **ConstraintPolicy 保守清理**: 10/11 零引用字段删除(GateProfile 已接管门禁),仅留 methodology_depth 唯一消费字段
