## 版本目标

激活 v5.9.0 项目类型框架的**第二个项目类型 `BINARY_APP`**——把原生客户端（桌面/移动）的构建链路打通：容器化构建 runtime 真正可用 + 二进制构建 + 产物落制品目录。同时落地 prompt-upgrade-plan #7（sufficiency 接线）+ ConstraintPolicy 死配置清理。

本版本结束 Arc 只能交付"静态站点"的单类型局限，向"不同项目类型落地"终局迈出第二步。

## 版本验证标准

1. 原生客户端项目经 DockerSandboxRuntime 容器化构建出**容器可构建目标二进制** — 按波次拆分:
   - 波次1 ✅: tauri linux bundle (deb/AppImage) — 镜像推导注入 + 自建 arc/tauri-builder:linux 镜像 + smoke 验证就绪
   - 波次2: web 资源 (镜像待建)
   - 波次3: android .apk (镜像待建)
2. `BinaryArtifactDeployer` 把二进制产物落制品目录（不签名不分发，签名在 v6.1）
3. ✅ sufficiency 接线：产出前门禁（产出前判断对话信息是否足够），替代纯轮次计数
4. ConstraintPolicy 死配置清理（gate_threshold 接管后的零引用字段）

> **跨平台范围决策（2026-06-24）**: 容器化 linux 沙箱无法构建 macOS .dmg / Windows .exe（需原生 OS，交叉编译支持有限）。v6.0 聚焦容器可构建目标；mac/win 原生二进制推后（原生 runner 或 CI matrix）。

### T7 — sufficiency 接线（已完成）
- **决策**: 产出前门禁方案（用户确认），非 plan 原推荐的轮次预筛+缓存(A+B)
- **理由**: 每轮注入"引导用户多说"不需要 LLM（轮次计数够用）；三维评估的真正价值是"产出前语义质量判断"，是门禁场景而非每轮注入。职责分离：轮次管引导，LLM 管质量判断。引入缓存复杂度高、用户补信息即失效，收益不明
- **实现**:
  - 新增 `execution/sufficiency_gate.py`: `SufficiencyResult` + `evaluate_sufficiency()` 调 `INPUT_SUFFICIENCY_PROMPT` 三维评估(target_users/core_problem/feature_direction)，降级放行（LLM 失败 → sufficient=True，遵循降级原则）
  - 接入 `ArtifactService.confirm()`: requirement_spec 确认前从 todo(title/desc) + 对话历史拼 summary → `evaluate_sufficiency`，sufficient=false 抛 ValueError（route 转 400 带 follow_up_questions）
  - `SufficiencyHintProvider` 简化: 移除 <4 轮质量判断（交门禁），保留 <2 轮早期粗引导
- **覆盖范围**: 对话模式 `confirm_artifact` route。pipeline 模式 `confirm_phase` 走 `evaluate_gate` 内容门禁兜底，sufficiency 漏检记遗留（#7 主语境是对话模式）
- **测试**: 单元 6（gate 逻辑/降级/解析）+ 集成 3（HTTP confirm 阻断/放行/非 requirement_spec 跳过）
- **遗留**: pipeline 模式 sufficiency 漏检（有 evaluate_gate 兜底，非阻塞）；test_health 时序污染仍存（v5.10 遗留）
